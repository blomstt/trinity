# 8. Scenes and entities: a handle-based world, hierarchy, scene instances with overrides

Date: 2026-10-17. Status: accepted.

## Context

E3 asks for entities and components, a node hierarchy, scene files that nest other scenes as instances with per-instance overrides, and an editor that edits all of it with undo, while staying small and NativeAOT-safe. Before E3 a scene was a flat list of `Node` objects (model, transform, clip, script) saved as JSON. The full specification (entity identity, components, hierarchy, instancing, serialization, editor, scripting, runtime, tests, staged delivery) came from blomst on 2026-10-17.

## Decision

- **A `World` of entity handles.** An `EntityId` is an index and a generation. Destroying an entity bumps its slot's generation, so old handles are detectably stale (`IsAlive`), and slots are reused. Per-entity data (name, transform, hierarchy links, cached world matrix, dirty flag, hidden flag, persistent id) lives in parallel arrays, not objects.
- **Components are plain structs in sparse sets** (`ComponentStore<T>`): one dense array of components and one of owners per type, with an index from entity to slot. At most one component of a type per entity; adding, removing and looking up are O(1); systems iterate the dense arrays. No archetypes: they pay off with many component combinations queried together, and Trinity has a handful of types and simple queries.
- **Built-in components:** `MeshRenderer` (a model path), `Animator` (clip, speed, paused, once), `Camera3D`, `DirectionalLight`, `ScriptComponent` (a script class and its saved field values), plus two the instancing system manages, `SceneInstance` and `Inherited`. Assets are referenced by project-relative path, so components hold no GPU objects and every renderer naming the same model shares one mesh.
- **Hierarchy in the world:** parent, first and last child, and siblings as linked indices, so child order is kept and moving a node is O(1) apart from the cycle check. `SetParent` refuses cycles and can keep the node's world transform. Transforms are local position, Euler rotation in degrees (as the inspector shows them) and scale. World matrices are computed when asked for and cached; changing a transform marks the node's subtree dirty, and the invariant that a dirty node's descendants are dirty lets marking stop early.
- **Changes during iteration are deferred.** While a system iterates (`BeginIteration`/`EndIteration`), destroying entities and removing components are queued and run at the end, so the arrays being walked don't shift. Creating entities and adding components is safe at any time; scripts added mid-update start at the next update.
- **`Node` is a handle**, a `World` plus an `EntityId`, with properties that read and write the world (`Name`, `Position`, `Children`, `Get<T>()`, `Destroy()`). Using a destroyed node throws; `IsValid` checks first. Scripts get their own node this way, and fields of type `Node` are filled from scene references.
- **Persistent ids for files, runtime ids for memory.** Each scene node has a 64-bit id unique within its scene file, with `NextId` saved alongside, so ids never repeat after deletions. A node inside an instance is named by a path of ids, `"7/3"` (node 3 of the scene instanced as node 7). References between nodes are saved as `{"$entity": "7/3"}` and become live `EntityId`s on load.
- **One property model, `SceneSchema`.** Every saved property is described once by hand: kind (text, number, bool, vector, asset, entity), getter and setter on a world. Saving, loading, override storage, the inspector and undo all go through it, so a property behaves the same everywhere. Written without reflection for NativeAOT. Script fields are properties too (`Script.Fields.Speed`).
- **Scene files, format 2:** nodes in hierarchy order (parents first), each with id, parent, name, transform, hidden, components as property bags, and for an instance its source scene and overrides. Loading validates: unknown format versions, bad or duplicate ids, parents listed after children are errors; unknown components or properties and wrong value types are warnings, and the rest of the file still loads. Format 1 (the flat list) is migrated on load.
- **Instances (prefabs):** a node with `SceneInstance` has the source scene's nodes as children, each marked `Inherited`. Inherited nodes aren't saved; the instance saves its source path and its overrides, keyed by source path and property (`{"3": {"Position": [0, 5, 0]}}`). Instances nest; overrides on nested nodes belong to the outermost instance. Loading rebuilds instances from their current sources, so edits to a source reach every instance on the next load (or at once, with Reload). A scene that contains itself is reported and not expanded. Overrides for nodes the source no longer has are kept but unused, with a warning, so they come back if the node does. A missing source leaves an empty instance and a warning.
- **The editor edits through `EditorScene`**, in the editor assembly: selection (a set, with a primary), edits that know about instances, and undo. Property edits record old and new values; drags merge into one step. Structural edits (create, delete, duplicate, reparent, components, reset override, instance) record whole-scene snapshots, and nodes are found again by persistent path after a restore. On an inherited node, a property edit becomes an override; deleting it, moving it or giving it components or children is refused, since that belongs to the source scene.
- **Script lifecycle:** scripts start after the scene is built; `Ready` runs children before parents (so a parent can rely on its children); `Update` and `FixedUpdate` run in the order scripts were added; `Destroyed` runs while the node and its components still exist. A script that throws is paused until its code changes (hot reload).
- **The runtime doesn't know about the editor.** `Trinity`, `Trinity.Rendering` and `Trinity.Graphics` don't reference the editor or ImGui; a test checks it.

## Consequences

- Per-frame scene work allocates nothing once warmed up (tested). At 5,000 nodes, moving every node and collecting draws costs 1.1 ms of CPU; collecting when nothing moved costs 0.1 ms (Release, JIT, Ryzen 7 9800X3D).
- Size: the Sandbox executable grew 83 KB (5.16 to 5.24 MB) and the editor 253 KB (5.96 to 6.21 MB). Peak memory running the sample scenes changed by under 1 MB.
- Snapshot undo is simple and complete, but costs O(scene): at 5,000 nodes a structural edit takes about 40 ms and its undo about 50 ms, with 2 MB of snapshot. Undo history is capped at 200 steps and 64 MB of snapshots; a big scene keeps fewer structural steps. Finer-grained commands can replace snapshots for the common cases if scenes outgrow this.
- Assets are referenced by path, so renaming or moving an asset file breaks references until a rename-aware asset database exists. Missing assets and scenes are reported, not fatal.
- The component set is fixed and built in; game-specific behaviour and data go in scripts. Games can add their own struct components at runtime, but those aren't saved or shown in the inspector until components can register themselves with `SceneSchema` (a source generator, as scripts have).
- Rotations are stored as Euler angles in degrees, which is what people type but can gimbal-lock in code that composes rotations; quaternions are computed from them for matrices.
- The gizmo moves the primary selection only, and the inspector edits the primary selection.
- Play runs the game as its own process with the saved scene, as before: what you see in Play is exactly the shipped game, at the cost of not inspecting the running world in the editor.
- An instance can't change which scene a nested instance points at (only properties of nodes inside it).
